# Apollo Reports: Operations How-To

Everything you need to run the daily and weekly reports without changing code. Read the IP doc first for context.

Most tasks are done through **Azure Cloud Shell** (portal.azure.com → click the `>_` icon in the top right) or the **Azure Portal**.

---

## 0. Access Prerequisites (do this first)

Before running any tasks below, get access to the Azure resources.

### Azure access (required for everything)

You need at least **Contributor** role on both resource groups:
- `apollo-reports-rg`
- `labor-util-rg`

Reader role is not enough, Contributor is needed to change app settings, deploy code, upload blobs, restart function apps, etc.

**Owner** role is optional but useful, it lets you manage IAM (add/remove users, rotate access keys via the Access Keys blade). Contributor can do most things.

**Who grants this:** whoever currently owns the Azure subscription. If Nathan has left, look for the subscription Owner in Portal → Subscriptions → Access control (IAM) → Role assignments (filter for "Owner").

**How access gets granted:**
1. Owner goes to Portal → **Subscriptions** → click subscription (`a867f16c-a3fa-49f1-947e-a1e364b73ddf`)
2. Left nav → **Access control (IAM)**
3. **Add** → **Add role assignment**
4. Role: **Contributor**
5. Assign to: your email address
6. Save

### Cloud Shell first-time setup

The first time you open Cloud Shell (Portal → `>_` icon in the top right), Azure will prompt you to create a storage account for Cloud Shell itself. Separate from `apolloreportsstorage`. Accept the defaults. One-time.

### GitHub access (for Static Web App changes)

To modify the reporting portal (add new report types, change display logic), you need write access to the `NathanM-Apollo/apollo-reporting` GitHub repo. Request from Nathan or whoever inherits ownership.

### Google Workspace access (only needed for password rotation)

To rotate the `GMAIL_APP_PASSWORD`, you need access to the Google account that owns `reports@apollobehavior.com`. Separate access from Azure, request from Apollo IT.

### If Cloud Shell home directory is empty

Cloud Shell's home directory is tied to the user who set it up. A new user gets an empty home, no deploy zips, no build scripts. Rebuild essentials:
- Deploy zips can be regenerated by re-extracting the last successful deploy from the function app (see Troubleshooting doc, "Emergency Rollback")
- Build scripts are inside those zips
- Manual wrapper scripts can be recreated from scratch

Not urgent for day-to-day operations. Only needed for a deploy or major maintenance.

## 1. Upload new billing data

Applies to all three functions (financial, supervision, parent training).

**Portal path:**
1. Portal → Storage accounts → `apolloreportsstorage`
2. Left nav → **Containers** → `apollo-reports`
3. Click into `inputs` → `billing`
4. Click **Upload** → pick file(s)
5. Check "Overwrite if files already exist" if replacing

**Naming rules:**
- File must be `.csv`
- Name can be anything (billing pattern is permissive)

**When it takes effect:** next scheduled run picks it up. No restart or deploy needed.

**Common pattern:** replace the current year's billing file every week or two with a fresh export covering the same period + more recent data.

---

## 2. Upload new receivables data

Only used by financial-daily.

**Same steps as billing, but:**
- Upload to `inputs/receivables/` (not billing)
- **Filename must contain the word "Receivables" (capital R)**: silently ignored otherwise

**Correct:** `2026-05-19 Receivables.csv`
**Wrong:** `Rec_20260519.csv` (missing "Receivables")

If AR numbers look tiny on the next run, this is the first thing to check.

## 3. Add a clinic (or change an address)

Applies to supervision AND parent training (both read the same mapping file).

The mapping is a blob file at `apollo-reports/config/clinics.csv`. To change it:

1. Portal → Storage accounts → `apolloreportsstorage` → Containers → `apollo-reports` → `config`
2. Click on `clinics.csv` → **Download**
3. Open in Excel
4. Add a row (or edit existing) with columns:
   - `StreetNumber`, leading digits of the clinic's address (unique across clinics)
   - `ClinicName`, display name that appears in the report
   - `FullAddress`, full street address (shown on reference tab)
5. Save as CSV (keep the filename)
6. Back to the blob folder → **Upload** → pick your edited CSV → check "Overwrite"

**When it takes effect:** next Monday's runs (both supervision and parent training pick it up).

**To roll up two addresses under one clinic** (e.g., during relocation): two rows with different StreetNumbers but same ClinicName.

**To hide a clinic that hasn't opened yet:** it can stay in clinics.csv without issues, the summary tabs automatically hide clinics with zero activity. It'll still appear in the "Clinic Mapping" reference tab.

**To remove a clinic:** delete its row. Sessions at that address fall into "Unmapped".

## 4. Add / remove email recipients

Recipients live in Function App application settings as JSON arrays.

### For daily financial report

Cloud Shell:

```bash
# REPLACES the list, include everyone you want
az functionapp config appsettings set \
  --name apollo-financial-reports-func \
  --resource-group apollo-reports-rg \
  --settings \
    'FINANCIAL_RECIPIENTS=["nathan.maziar@apollobehavior.com","kim.dean@apollobehavior.com","new.person@apollobehavior.com"]' \
  --output none

# Verify
az functionapp config appsettings list \
  --name apollo-financial-reports-func \
  --resource-group apollo-reports-rg \
  --query "[?name=='FINANCIAL_RECIPIENTS'].value" \
  --output tsv
```

### For weekly supervision report

Same commands but on `apollo-supervision-func` with `SUPERVISION_RECIPIENTS`.

### For weekly parent training report

Same function app (`apollo-supervision-func`) but `PARENT_TRAINING_RECIPIENTS`.

```bash
az functionapp config appsettings set \
  --name apollo-supervision-func \
  --resource-group apollo-reports-rg \
  --settings \
    'PARENT_TRAINING_RECIPIENTS=["nathan.maziar@apollobehavior.com","new.person@apollobehavior.com"]' \
  --output none
```

### Client & Insurance Roster

No report email. Only failure notices, set with `CLIENT_ROSTER_ERROR_RECIPIENTS` on `apollo-supervision-func` (same JSON array format). If the setting isn't there, failure notices go to Nathan.

**When it takes effect:** next scheduled run. No restart or deploy needed.

**Portal path if you prefer clicks:** Portal → Function App → Environment variables → App settings → find setting → Edit → save.

## 5. Manually trigger a run (for testing)

Two ways:

### Portal
1. Portal → Function App → **Functions** → click the function name (`financial-daily`, `supervision-weekly`, `parent-training-weekly`, or `client-roster-weekly`)
2. Left sidebar → **Code + Test**
3. Click **Test/Run** tab at the top
4. Click green **Run** button

Expected: within 30s you see log lines. Full run: 3-5 min for financial, 5-8 for supervision, 5-8 for parent training, 2-4 for the client roster. Recipients get email at completion. The client roster sends no email; check the portal or `outputs/client-roster/` in storage instead.

A manual run of `financial-daily`, `supervision-weekly`, or `parent-training-weekly` emails the full recipient list. To refresh only the portal, run the build script in Cloud Shell and upload the file to `outputs/{report}/{YYYY-MM-DD}/` instead.

Portal sometimes shows "Failed to fetch" at click time, transient. Refresh and retry.

### Cloud Shell (more reliable if Portal is glitchy)

```bash
# For supervision (or replace with financial or parent-training)
SUB_ID=$(az account show --query id -o tsv)
FUNC_APP=apollo-supervision-func
FUNC_NAME=supervision-weekly    # or parent-training-weekly, or client-roster-weekly

az rest --method POST \
  --uri "https://management.azure.com/subscriptions/$SUB_ID/resourceGroups/apollo-reports-rg/providers/Microsoft.Web/sites/$FUNC_APP/host/default/listKeys?api-version=2022-03-01" \
  --query "masterKey" -o tsv > /tmp/funckey.txt

curl -X POST \
  -H "x-functions-key: $(cat /tmp/funckey.txt)" \
  "https://$FUNC_APP.azurewebsites.net/admin/functions/$FUNC_NAME" \
  -H "Content-Type: application/json" \
  -d '{"input":""}' \
  -w "\nHTTP status: %{http_code}\n"
```

Expected: `HTTP status: 202` = triggered. Then wait for email.

## 6. Change the schedule

Requires a deploy since `function.json` is in the deploy zip.

**Cron format:** `SECOND MINUTE HOUR DAY MONTH DAYOFWEEK`
- Financial default: `0 30 7 * * 1-5` (weekdays 7:30 AM)
- Supervision default: `0 0 8 * * 1` (Monday 8:00 AM)
- Parent training default: `0 30 8 * * 1` (Monday 8:30 AM)
- Client roster default: `0 0 9 * * 1-5` (weekdays 9:00 AM), function `client-roster-weekly`
- Time is in `WEBSITE_TIME_ZONE` (currently `America/New_York`)

**Steps:**

1. Unpack the latest deploy zip:
   ```bash
   mkdir -p /tmp/edit && cd /tmp/edit && rm -rf *
   unzip -o ~/apollo-supervision-deploy-v10.zip > /dev/null
   ```

2. Edit the `function.json` for the function you want to change (e.g., `parent-training-weekly/function.json`): change the `schedule` field.

3. Rezip and deploy:
   ```bash
   cd /tmp/edit
   rm -f ~/apollo-supervision-deploy-schedule-change.zip
   zip -r ~/apollo-supervision-deploy-schedule-change.zip . -x "*.pyc" "__pycache__/*"
   
   az webapp deploy \
     --resource-group apollo-reports-rg \
     --name apollo-supervision-func \
     --src-path ~/apollo-supervision-deploy-schedule-change.zip \
     --type zip
   ```

4. Verify:
   ```bash
   az functionapp function show \
     --name apollo-supervision-func \
     --resource-group apollo-reports-rg \
     --function-name parent-training-weekly \
     --query "config.bindings[0].schedule" -o tsv
   ```

## 7. Stop / start a function

Applies to the entire function app, not individual functions. Stopping `apollo-supervision-func` stops both supervision AND parent training.

**Stop:**
```bash
az functionapp stop \
  --name apollo-supervision-func \
  --resource-group apollo-reports-rg
```

**Start:**
```bash
az functionapp start \
  --name apollo-supervision-func \
  --resource-group apollo-reports-rg
```

**Restart** (does not stop scheduled runs, just refreshes the host):
```bash
az functionapp restart \
  --name apollo-supervision-func \
  --resource-group apollo-reports-rg
```

Use restart if the function is misbehaving after a deploy or config change.

Stopping preserves settings, code, and blob data. It just prevents timer firing.

```bash
# Parent training
az functionapp function show \
  --name apollo-supervision-func \
  --resource-group apollo-reports-rg \
  --function-name parent-training-weekly \
  --query "config.bindings[0].schedule" -o tsv

# Client roster (should be 0 0 9 * * 1-5)
az functionapp function show \
  --name apollo-supervision-func \
  --resource-group apollo-reports-rg \
  --function-name client-roster-weekly \
  --query "config.bindings[0].schedule" -o tsv

# Timezone (should be America/New_York on both apps)
az functionapp config appsettings list \
  --name apollo-supervision-func \
  --resource-group apollo-reports-rg \
  --query "[?name=='WEBSITE_TIME_ZONE'].value" -o tsv
```

Wrong timezone → cron fires at UTC (usually 4 hours off, middle of the night Eastern). Fix:
```bash
az functionapp config appsettings set \
  --name apollo-supervision-func \
  --resource-group apollo-reports-rg \
  --settings "WEBSITE_TIME_ZONE=America/New_York" \
  --output none
```

## 9. Confirm a run succeeded

**Easiest:** check inbox. Success email subjects: `Apollo Daily Financial Reports, YYYY-MM-DD`, `Apollo Supervision Ratio, YYYY-MM-DD`, `Apollo Parent Training, YYYY-MM-DD`. Failure emails start with `[FAILED]`.

**Also check the Static Web App:** load the portal, click into the report, most recent dated folder becomes the visible version.

**Via Azure CLI:**
```bash
SUB_ID=$(az account show --query id -o tsv)
az monitor metrics list \
  --resource "/subscriptions/$SUB_ID/resourceGroups/apollo-reports-rg/providers/Microsoft.Web/sites/apollo-supervision-func" \
  --metric "FunctionExecutionCount" \
  --interval PT5M \
  --start-time $(date -u -d '4 hours ago' +%Y-%m-%dT%H:%M:%SZ) \
  --query "value[0].timeseries[0].data[?total > \`0\`]" \
  --output table
```

Rows with `total > 0` indicate the function ran at that time. Both supervision and parent training count toward this single app-level metric.

**Also check the output was archived to blob:**
Portal → apolloreportsstorage → Containers → apollo-reports → outputs → {revenue/ar/supervision/parent-training} → date folders

## 10. Add a new report to the Static Web App

If you're building a new function that should appear on the portal:

**Function-side:**
- Build script produces an XLSX
- Orchestrator writes it to blob at `outputs/{new-key}/{date}/*.xlsx`

**SWA-side (one commit to the GitHub repo):**

1. Clone or pull the repo:
   ```bash
   cd ~/apollo-reporting
   git pull
   ```

2. Edit `prod/api/shared/access.py`, add to `REPORT_CATALOG`:
   ```python
   "new-key": {"title": "Display Title", "scope": "all", "folder": "outputs/new-key"},
   ```

3. Commit + push:
   ```bash
   git add prod/api/shared/access.py
   git commit -m "Add new-key report to catalog"
   git push
   ```

   To let a group other than `apollo_et` see it, add the key to that group's `reports` set in the same file. For example, RCM's line reads `"reports": {"ar", "rev", "client-roster"}`.

4. Wait 2-3 min. GitHub Actions auto-deploys the SWA.

5. First time the function runs and writes to blob, the SWA will pick it up on next page load.

**Important gotcha for hour-valued reports:** the SWA classifier heuristics misclassify fractional-under-1 values as percentages. If your report has hour columns like parent training's, either add "hrs" to the column headers OR extend the classifier in `prod/web/index.html`.

## 11. Rotate credentials

**Gmail App Password:**

1. Log into the Google account owning `reports@apollobehavior.com`
2. Go to https://myaccount.google.com/apppasswords
3. Delete old "Apollo Reports Function" app password
4. Create new one with same name
5. Copy the 16-character password
6. Update both function apps:
   ```bash
   NEW_PASS='xxxx xxxx xxxx xxxx'
   
   az functionapp config appsettings set \
     --name apollo-financial-reports-func \
     --resource-group apollo-reports-rg \
     --settings "GMAIL_APP_PASSWORD=$NEW_PASS" \
     --output none
   
   az functionapp config appsettings set \
     --name apollo-supervision-func \
     --resource-group apollo-reports-rg \
     --settings "GMAIL_APP_PASSWORD=$NEW_PASS" \
     --output none
   ```
7. Trigger manual runs of each function to verify email still sends

**Storage account keys** (Portal → apolloreportsstorage → Access keys → Rotate key1 or key2):

Both function apps use the storage account connection string in `AzureWebJobsStorage`. If you rotate a key:

1. Get new connection string:
   ```bash
   az storage account show-connection-string \
     --name apolloreportsstorage \
     --resource-group apollo-reports-rg \
     --query connectionString -o tsv
   ```
2. Update both function apps with the new string (same pattern as Gmail above, setting is `AzureWebJobsStorage`)
3. Restart both function apps

Do rotations during quiet windows (evening or weekend): mid-execution rotation can cause a failed run.

## 12. Client headcount by month (97153)

A standalone script, not on the portal. It builds Month | Beg Headcount | Adds | Churn | End Headcount from Jan-25 through Sep-26, using 97153 billing only.

**Where it lives:** `tools/client_headcount.py` in the `apollo-reporting` GitHub repo, and `~/client_headcount.py` in Cloud Shell.

**Rules:**
- A client stays active as long as no gap between 97153 visits is longer than 150 days. Shorter breaks (vacation, insurance pauses) don't count as a churn or a new add.
- Adds count in the month of the client's first visit, or first visit back after a gap longer than 150 days.
- Churn counts in the month of the client's last visit before a gap longer than 150 days. A client with no 97153 in the newest month counts as churned for now. If they come back within 150 days, the next run removes that churn, since the table is rebuilt from all billing each time.
- Beg Headcount = prior month's End. Each row ties out: Beg + Adds − Churn = End.
- The newest month's churn shows 0, since anyone billed that month is active. Adjust it by hand for known mid-month stops.
- Billing before Jan-25 (back to 2021) is used to work out who was active going in.

**To change the months covered:** edit `REPORT_START` and `REPORT_END` near the top of the script.

**To run it:**

```bash
mkdir -p /tmp/hc/dl
az storage blob download-batch --source apollo-reports --pattern "inputs/billing/*" --destination /tmp/hc/dl --connection-string "$(az storage account show-connection-string --name apolloreportsstorage --resource-group apollo-reports-rg --query connectionString -o tsv)" --output none
pip install --user --quiet pandas openpyxl
python3 ~/client_headcount.py /tmp/hc/dl ~/client_headcount.xlsx
```

Then download `client_headcount.xlsx` from Cloud Shell (Manage files → Download).
